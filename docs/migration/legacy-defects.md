# Legacy defects found during A308 review

These defects are in the running legacy Caspar node. The migration preserves the
**observable** legacy state and never silently repairs it. Fixing the legacy node is
tracked separately, and security rows should be fixed before cutover. A fix made while
rewiring an action family onto ports is recorded in its row, together with its test.

| ID | Severity | Legacy evidence | Defect | Migration handling |
|---|---|---|---|---|
| LD-01 | Security (critical) | `shell/api/actions/creature.rs` `/creatures/login` | Returns the account's stored RSA private key on every email login; with Firebase disabled, any email is accepted | ADR 0019: keys verified, never exported; RL-019 |
| LD-02 | Security (high) | `creature.rs` `secret_revoke` | Deletes `SecretGrant::…` without the `link::` prefix, so revocation never takes effect and grants stay valid until an unbounded expiry | ADR 0023: grants migrate as legacy enforces them; fix: prefix both deletes with `link::` |
| LD-03 | Security (medium) | `shell/utils/secret_crypto.rs` | Secret ciphertext carries no AAD, so a blob moved to another owner or name still decrypts | ADR 0023: P4 re-wraps with owner/name/epoch AAD before delivery |
| LD-04 | Functional | `creature.rs` `secret_list`, `list_granted_secrets` | Raw `get_by_prefix` never matches `link::` records, so the lists are always empty | Not migrated state; P4 implements listing correctly |
| LD-05 | Functional | `drivers/vmm/driver.rs` guest `dbOp` | `del` removes an unprefixed key (a no-op), and `getByPrefix` scans raw keys (never returns committed pairs) | ADR 0021: committed pairs migrate; the P4-04 gateway fixes both |
| LD-06 | Data retention | `hostcall_entities.rs` store and resource deletes | `Json::StoreMeta`, `Json::VmResourceStore`, and `Json::VmResourceEntity` deletes use unprefixed raw keys, leaving orphaned documents | ADRs 0016/0022: orphans fail closed or migrate as observed by `get`. Fixed for stores by the store strangler: store and creature deletes remove `StoreMeta` through `StoreMetadata` |
| LD-07 | Finance | `creature.rs`/`program.rs` `as_i64` | Float amounts are truncated to integers | ADR 0017: non-integer money fails closed |
| LD-08 | Finance | `program.rs` billing sweep | Stale `VmStatus = running` records keep being billed after a restart, because instances are never relaunched | ADR 0022: P8 reconciles against observed runtime |
| LD-09 | Dead state | `core/core_orchestrator.rs` | `chainCallback::*` is written and never consumed or deleted | ADR 0020: dropped after shape checks |
| LD-10 | Durability | `core/actor/model/trx.rs` `commit` | The batch write result is discarded, so a failed commit is silently lost while the caller sees success | Fixed (ADR 0026 prerequisite): `ITrx::commit` returns the write error and replicates nothing for a failed batch. `modify_state` logs it, and secured actions fail with it through `modify_state_securly_checked`. Test: `a_failed_commit_is_reported` |
| LD-11 | Functional | `shell/api/actions/store.rs` `/stores/setAccess` | Writes only `onaccess`, never `hasaccess`: granting access to a non-member creates a one-sided pair that guards ignore | ADR 0018 export fails closed on one-sided pairs; target membership is a single record, so a grant makes the grantee a member (documented behavior change) |
| LD-12 | Functional | `creature.rs` `/creatures/delete`; `hostcall_entities.rs` creature `delete` | Both walk memberships with `Store::list(.., -1, -1)`. `search_link_keys_list_by_prefix` stops at `counter >= offset + count` (0 ≥ −2), so the walk is always empty. A deleted creature keeps every `onaccess`/`hasaccess` pair, and stores it solely owned are never deleted | Fixed in the node by the RL-004 store strangler: both paths call `LegacyMembership::remove_member_everywhere` (test `removing_a_member_everywhere_fixes_the_empty_legacy_walk`). Pairs left by earlier deletions are dangling local members, which the ADR 0018 export fails closed on. The audited pre-export repair (ADR 0018 amendment; runbook prerequisite 6) removes them under an approved digest |
| LD-13 | Functional | `creature.rs` `/creatures/update`, `/creatures/delete`, `/creatures/meta`; VM `updateCreature` | `Creature::pull` keeps the requested id, so each `user.id.is_empty()` check is dead code. Updating a missing id (as `1@global`, or through the VM host call) writes a partial Creature record with no balance. Deleting or reading one succeeds with nothing to act on | Fixed by the RL-004 creature strangler: the use cases read through `CreatureDirectory`, and a missing creature is `user not found` (VM: `creature not found`). The same dead check in the finance balance sites, login, and the reconciliation audit is fixed too: a credit can no longer create a partial Creature, login drops a stale email link, and the audit reports orphaned withdrawable counters. The VM `getCreature` keeps its legacy empty-creature answer. Tests: `aseman-application` creature tests |
| LD-14 | Security (critical) | `hostcall_entities.rs` `handle_creature_crud` (`createCreature`, `updateCreature`, `deleteCreature`) | No authorization. Any VM guest can create, overwrite, or delete any creature and set any balance. `createCreature` overwrote existing records and could take over another creature's username index | Fixed in P4-04/P4-05. Every guest host call is authorized as its A402 action with server-resolved facts: creature, store, access, program, workload, and resource targets must belong to the caller's owner or grant it membership. A creature a guest creates is owned by the guest's owner and cannot be funded. The identity-less paths are closed: `vm_callback` serves only runtime events, `protocolApi` is refused, unknown calls are refused, and runtimes no longer dispatch typed or raw packets. LD-27 fixed the forged identity underneath |
| LD-15 | Atomicity | `core/actor/model/secured/action.rs` (all three dispatch paths); `hostcall_entities.rs` VM `signal` | The Rust translation's state closure always returned `Ok(())`, so a failed action's partial writes were committed. The Go original returns the action's error, which discards the transaction | Fixed: the closures return the action's error, so its writes are discarded as in Go (`node.old` `secured/action.go`). A failed commit now fails the action (LD-10). There is no action-level harness for this path yet; the Go source is the parity evidence |
| LD-16 | Data integrity | `creature.rs` / VM `createCreature`, `updateCreature`, creature deletes | The derived `ownerof::{owner}::{creature}` link was written only at create. Deletes left it pointing at a missing creature, and owner or type changes left it naming a stale owner. The A308 export verifies the link against `ownerId`, so either residue blocks the export | Fixed in the node: the legacy creature adapter derives the link on create, update, and delete (test `owner_links_follow_the_record`). The pre-export repair removes dangling and stale links and rebuilds missing ones from `ownerId` under the approved digest. A machine without an `ownerId` is left for an operator (test `owner_link_repair_rebuilds_links_from_owner_ids`) |
| LD-17 | Functional / data integrity | `program.rs` `/programs/delete`; VM `deleteProgram`, `deployEntity`, `createProgram`, `updateProgram` | `/programs/delete` resolved the machine through a `Program id→programId` index that is never written: it pushed a Creature with an empty id, and removed neither the program nor its link. The VM delete removed only the `machinePrograms` link and kept the program. VM deploy into a missing program created a bare program with no `machineId`, and VM create/update wrote partial records. The A308 export rejects a program without its link or machine | Fixed by the program strangler (`ProgramDirectory`): deletes remove the program, its metadata, and its link; deploy, create, and update refuse a missing program or machine. The pre-export repair removes dangling and stale `machinePrograms` links, rebuilds missing ones from `machineId`, and reports bare programs for an operator (test `program_link_repair_rebuilds_links_and_reports_bare_programs`) |
| LD-18 | Security (medium) | `program.rs` `/programs/update`, `/programs/delete` | No ownership check: any authenticated user could change any program's path and metadata. Delete was harmless only because LD-17 made it a no-op | Fixed: `aseman-application::program` allows only the owner of the program's machine to update or delete it, the rule `/programs/create` already applied. The VM host calls remain unauthorized until the P4 gateway (LD-14) |
| LD-19 | Functional | `hostcall_entities.rs` `plantTrigger` alarm thread | After sleeping, each alarm thread cleared the program's alarm unconditionally. When a newer alarm was planted meanwhile, the older thread erased it, so a restart would not replay it | Fixed by the program-alarm strangler: the drain clears the alarm only if it is still the one this thread planted (`ProgramAlarms`) |
| LD-20 | Functional | `fednet.rs` `stores/delete`, `stores/update`; VM `listStores`, `createStore` | A mirrored store delete removed the key `obj::Store::{id}`, which never exists, so it did nothing. A mirrored update of an unknown store recreated it without a creator. VM `listStores` without a user searched links for `obj::Store::` and was always empty. VM `createStore` accepted a store without a creator, which the export cannot own | Fixed by the store strangler: federated deletes remove the store and its metadata, updates of unknown stores are ignored, the list returns the first 50 stores, and a VM store needs a creator. The pre-export repair reports stores whose parent is missing or is themselves |
| LD-21 | Data integrity | `hostcall_entities.rs` VM resource stores (`createStore`/`updateStore`, `deleteStore`, `listStores`) | An update without `machineId` overwrote the owner with an empty string, which orphans the store; the A308 export rejects it. A store could be created without a machine. Deletes used unprefixed raw keys (LD-06) and removed nothing. Listing all stores scanned a raw prefix and returned nothing | Fixed by the resource-store strangler (`VmResourceStores`): an update keeps the owner, a new store needs a machine, deletes remove the documents and the ownership link, and the all-stores listing works (same wire format). The A308 export now also emits legacy identities for resource stores, so they can be listed by id after cutover |
| LD-22 | Functional | `drivers/network/chain/blockchain.rs` `restore_chains_from_storage_inner` | `Chain::all(trx, -1, -1)` and `ChainShard::all(trx, -1, -1)` hit the `count = -1` window (as LD-12), so persisted work chains and shards are never restored on restart | Not changed in Phase 3: restoring would start a consensus engine per chain at boot, which has never run in production. The chain family stays with the consensus provider until P8 (ADR 0026), which owns the fix |
| LD-23 | Data integrity | `blockchain.rs` `create_new_shard_chain(.., "shard-main", ..)` | Every work chain persists its main shard under the one id `shard-main`, so each new chain overwrites the previous chain's main shard record | Recorded for P8 with LD-22; the A308 export migrates the surviving record as observed |
| LD-24 | Security (critical) | `host_bridge.rs` `vm_json_trx_op` (`putJson`, `getJson`, `getByPrefix`, `delKey`), reached from the JavaScript and WASM runtimes; `hostcall_entities.rs` `putJson`/`getJson` | A VM guest reads, writes, and deletes arbitrary keys in the node's store, with no namespace. It can forge or delete finance holds, pools, journals, and balances, secrets, sessions, and core documents | Fixed by ADR 0028 (P4-04): the calls are confined to the calling creature (`GuestDoc::{creature}::` documents, and `getLink` limited to its own `dbOp` pairs), refused without a trusted creature, and refused on the identity-less `vm_callback` protocol. The documents migrate into the creature's guest database. LD-27 (forged caller identity) is fixed alongside |
| LD-25 | Security (high) | `program.rs` `programs/deploy` extra files, `hostcall_entities.rs` VM entity deploy, `cluster/mod.rs` artifact replication | The names of a deploy's extra files come from the request (`metadata.files` keys) and were written as `{build_folder}/{name}`. A name such as `../../x` escaped the entity folder, which let a deployer write any file the node can write | Fixed by ADR 0027: every deploy file goes through the `BlobStore` port (`put_entity_file`), whose keys cannot be absolute or contain `.`/`..` segments. A rejected name fails the deploy. Covered by the node blob-store test |
| LD-26 | Security (high) | `hostcall_entities.rs` `createResourceEntity` / `deleteResourceEntity` | The data file was written to `{root}/vm_stores/{store}/{type}/{id}.json` from guest-supplied parts, so `entityType: "../.."` wrote or deleted any `.json` file the node can reach. A part containing `::` produced a key the A308 export rejects. An entity could name a resource store that does not exist, which the export also rejects. The delete removed raw keys the JSON encoding never writes, so deleted entities survived. Failures were reported as success | Fixed by the resource-entity strangler (`VmResourceEntities`, `PutResourceEntity`, `DeleteResourceEntity`): every part must be one key segment without `::`, which is checked before any file is written. The data goes through the ADR 0027 blob store, and a missing store is refused and its data removed. Deletes remove both documents and the data file, and failures return `ok: false` |
| LD-27 | Security (critical) | `vm_host_functions.rs` `resolve_host_hierarchy` / `resolve_cached_vm_hierarchy`; `docker_host/dispatch.rs` | Host calls took the caller's `vmId` from the packet, but fell back to the guest-controlled `input.vmId` when the packet had none. The docker gateway stamped identity only into `input`, and kept the guest's own `vmId` when a container had no verified identity. The fallback selected another VM's registered context, so a guest could act as that VM's creature: `secretGet`, `secretListGranted`, `execShellAction`, and `dbOp` namespacing | Fixed in P4-04: caller identity is read only from the packet. The docker gateway stamps its verified identity at packet level and refuses containers without one. Covered by node tests |
