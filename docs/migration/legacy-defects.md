# Legacy defects found during A308 review

These defects are in the running legacy Caspar node. The migration preserves the
**observable** legacy state and never silently repairs it. Fixing the legacy node is
tracked separately, and security rows should be fixed before cutover. A fix made while
rewiring an action family onto ports is recorded in its row, together with its test.

| ID | Severity | Legacy evidence | Defect | Migration handling |
|---|---|---|---|---|
| LD-01 | Security (critical) | `shell/api/actions/creature.rs` `/creatures/login` | Returns the account's stored RSA private key on every email login; with Firebase disabled, any email is accepted | ADR 0019: keys verified, never exported; RL-019 |
| LD-02 | Security (high) | `creature.rs` `secret_revoke` | Deletes `SecretGrant::…` without the `link::` prefix, so revocation never takes effect and grants stay valid until an unbounded expiry | ADR 0023: grants migrate as legacy enforces them; fix: prefix both deletes with `link::` |
| LD-03 | Security (medium) | `shell/utils/secret_crypto.rs` | Secret ciphertext carries no AAD, so a blob moved to another owner or name still decrypts | ADR 0023: P4 re-wraps with owner/name/epoch AAD before delivery |
| LD-04 | Functional | `creature.rs` `secret_list`, `list_granted_secrets` | Raw `get_by_prefix` never matches `link::` records, so the lists are always empty | Not migrated state; P4 implements listing correctly |
| LD-05 | Functional | `drivers/vmm/driver.rs` guest `dbOp` | `del` removes an unprefixed key (a no-op), and `getByPrefix` scans raw keys (never returns committed pairs) | ADR 0021: committed pairs migrate; the P4-04 gateway fixes both |
| LD-06 | Data retention | `hostcall_entities.rs` store and resource deletes | `Json::StoreMeta`, `Json::VmResourceStore`, and `Json::VmResourceEntity` deletes use unprefixed raw keys, leaving orphaned documents | ADRs 0016/0022: orphans fail closed or migrate as observed by `get` |
| LD-07 | Finance | `creature.rs`/`program.rs` `as_i64` | Float amounts are truncated to integers | ADR 0017: non-integer money fails closed |
| LD-08 | Finance | `program.rs` billing sweep | Stale `VmStatus = running` records keep being billed after a restart, because instances are never relaunched | ADR 0022: P8 reconciles against observed runtime |
| LD-09 | Dead state | `core/core_orchestrator.rs` | `chainCallback::*` is written and never consumed or deleted | ADR 0020: dropped after shape checks |
| LD-10 | Durability | `core/actor/model/trx.rs` `commit` | The batch write result is discarded, so a failed commit is silently lost while the caller sees success | Fixed (ADR 0026 prerequisite): `ITrx::commit` returns the write error and replicates nothing for a failed batch. `modify_state` logs it, and secured actions fail with it through `modify_state_securly_checked`. Test: `a_failed_commit_is_reported` |
| LD-11 | Functional | `shell/api/actions/store.rs` `/stores/setAccess` | Writes only `onaccess`, never `hasaccess`: granting access to a non-member creates a one-sided pair that guards ignore | ADR 0018 export fails closed on one-sided pairs; target membership is a single record, so a grant makes the grantee a member (documented behavior change) |
| LD-12 | Functional | `creature.rs` `/creatures/delete`; `hostcall_entities.rs` creature `delete` | Both walk memberships with `Store::list(.., -1, -1)`. `search_link_keys_list_by_prefix` stops at `counter >= offset + count` (0 ≥ −2), so the walk is always empty. A deleted creature keeps every `onaccess`/`hasaccess` pair, and stores it solely owned are never deleted | Fixed in the node by the RL-004 store strangler: both paths call `LegacyMembership::remove_member_everywhere` (test `removing_a_member_everywhere_fixes_the_empty_legacy_walk`). Pairs left by earlier deletions are dangling local members, which the ADR 0018 export fails closed on. The audited pre-export repair (ADR 0018 amendment; runbook prerequisite 6) removes them under an approved digest |
| LD-13 | Functional | `creature.rs` `/creatures/update`, `/creatures/delete`, `/creatures/meta`; VM `updateCreature` | `Creature::pull` keeps the requested id, so each `user.id.is_empty()` check is dead code. Updating a missing id (as `1@global`, or through the VM host call) writes a partial Creature record with no balance. Deleting or reading one succeeds with nothing to act on | Fixed by the RL-004 creature strangler: the use cases read through `CreatureDirectory`, and a missing creature is `user not found` (VM: `creature not found`). The same dead check in the finance balance sites, login, and the reconciliation audit is fixed too: a credit can no longer create a partial Creature, login drops a stale email link, and the audit reports orphaned withdrawable counters. The VM `getCreature` keeps its legacy empty-creature answer. Tests: `aseman-application` creature tests |
| LD-14 | Security (critical) | `hostcall_entities.rs` `handle_creature_crud` (`createCreature`, `updateCreature`, `deleteCreature`) | No authorization. Any VM guest can create, overwrite, or delete any creature and set any balance. `createCreature` overwrote existing records and could take over another creature's username index | Partly mitigated by the creature strangler: create refuses an existing id or username (no overwrite or index takeover), and update refuses a missing creature. Authorization is owned by the P4 guest gateway (host calls move to the authenticated guest API); fix before cutover |
| LD-15 | Atomicity | `core/actor/model/secured/action.rs` (all three dispatch paths); `hostcall_entities.rs` VM `signal` | The Rust translation's state closure always returned `Ok(())`, so a failed action's partial writes were committed. The Go original returns the action's error, which discards the transaction | Fixed: the closures return the action's error, so its writes are discarded as in Go (`node.old` `secured/action.go`). A failed commit now fails the action (LD-10). There is no action-level harness for this path yet; the Go source is the parity evidence |
| LD-16 | Data integrity | `creature.rs` / VM `createCreature`, `updateCreature`, creature deletes | The derived `ownerof::{owner}::{creature}` link was written only at create. Deletes left it pointing at a missing creature, and owner or type changes left it naming a stale owner. The A308 export verifies the link against `ownerId`, so either residue blocks the export | Fixed in the node: the legacy creature adapter derives the link on create, update, and delete (test `owner_links_follow_the_record`). The pre-export repair removes dangling and stale links and rebuilds missing ones from `ownerId` under the approved digest. A machine without an `ownerId` is left for an operator (test `owner_link_repair_rebuilds_links_from_owner_ids`) |
