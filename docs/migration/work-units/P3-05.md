# P3-05 legacy storage and canonical transfer work record

## Requirement and ownership

P3-05 implements A308 and the export/import portion of A309 under ADR 0001, ADR 0006,
ADR 0007, ADR 0012, and ADR 0014. RL-005 owns legacy storage replacement; RL-006,
RL-008, RL-011, and RL-012 own guest, realtime, finance-consensus, and OpenRaft paths.
No current provider authority is changed and no legacy key or database is deletable.

## Implemented so far

- A versioned canonical capsule stream with source snapshot and transform-manifest binding,
  ordered records, domain-separated stream digest, record count, and resumable checkpoints.
  Canonical capsule validation rejects mutation, reordering, omission, and forged resume
  state before import.
- A bounded read-only RocksDB snapshot source isolated in `aseman-storage-legacy`, plus
  strict transformer and idempotent import-sink interfaces. An unmapped physical record is
  a hard error; opaque bytes are never promoted into authoritative target state.
- Deterministic domain-separated legacy identity derivation and bounded batch import with
  inserted/already-present accounting.
- Fixture-backed transforms for legacy `Program`, `Entity`, `Store`, `Chain`, and
  `ChainShard` families and QuestDB `buildlogs`. Entity/program ownership, store creator
  links, and chain ownership are resolved by
  the server-side snapshot graph. Build-log tenancy comes from a resolved VM-to-creature binding,
  conflicting row ownership fails closed, and legacy milliseconds convert exactly to
  canonical microseconds.
- Legacy bearer sessions become deterministic digest-only revocation capsules. Unknown
  issue/expiry times remain zero and every record is revoked at migration time; no legacy
  session is activated or granted a longer lifetime by the migration.
- Legacy `File` metadata emits only when the migration runner supplies bounded external
  byte evidence (target store key, exact size, media type, and SHA-256 digest). A missing
  filesystem object or copy proof fails the export instead of producing a dangling file.
- The unified legacy `Creature` row splits into a user (for humans), an ownership-boundary
  creature, and a wallet. RSA SPKI is parsed and tagged as the ADR 0009 legacy multicodec
  verification epoch; chain/subchain routing strings are preserved. Wallet conversion
  requires an explicit uppercase currency and decimal scale, so no token precision is guessed.
- QuestDB signal history sorts deterministically by store/time/ID into immutable per-store
  realtime sequences. The payload preserves data, validated tags, edit state, and legacy IDs;
  authorization scope and retention must be resolved from the store graph, never from the row.
- The target shard schema preserves the legacy named shard identity (`shard-main` and
  provider-defined names) instead of assuming a numeric shard index. Existing persisted
  chain rows receive the explicit migration state `active`; no missing row is synthesized.
- ADR 0016 legacy JSON document families. `json::{key}::{path}` records assemble into
  per-key documents. The reviewed `UserMeta`, `CreatMeta`, `StoreMeta`, and `ProgMeta`
  roots at `metadata` become `core.user_metadata`, `core.creature_metadata`,
  `core.store_metadata`, and `core.program_metadata` capsules. Each capsule holds a structured
  document value (no JSONB, no opaque bytes), `entry_count`, a domain-separated
  `content_digest`, and a typed, server-resolved subject relationship.
  `UserMeta`/`CreatMeta` stay separate because legacy deletes them through different
  actions. Every `metadata.*` splat is rebuilt from the root and compared. A stale,
  unequal, missing, or foreign-path splat fails closed, and so does an orphaned document
  whose subject is absent (legacy store deletion removes the wrong key and leaves
  `StoreMeta` behind), a non-object root, or a number outside the capsule range. Any other
  `json::` key family is `Unmapped`. The PostgreSQL provider maps `document` fields to no
  column, requires a capsule object, and rejects filtering or sorting on them.
- A generated transform manifest that accounts for every A004 direct access, candidate
  key, physical layout, typed object, QuestDB table, Hashgraph family, and OpenRaft store.
  Derived indexes/links are rebuilt and compared rather than migrated as authorities.

## Link/index authority and A004 correction

- The A004 scanner truncated every file at its first `#[cfg(test)]`. Because
  `creature/finance.rs` opens with a small test module, most legacy finance persistence was
  never inventoried. The scanner now blanks only `#[cfg(test)]` items and keeps line
  numbers. A004 grew from 243 to 292 direct accesses and from 306 to 358 candidate
  templates.
- The manifest used to classify every link and index access as a rebuildable projection,
  but many link families hold primary state: `UserPrivateKey`,
  `FinanceDebt`/`Held`/`Withdrawable`/`PayoutHeld` balances, `hasaccess`/`onaccess`
  memberships and permissions, and VM status/alarm/entity fields. The export previously
  ignored any link it did not consume, which would have dropped that state silently.
- The export now verifies every link and index before emitting capsules.
  - `creatorof` and `UserIdToEmail` are consumed by transforms. `UserIdToEmail` and
    `UserEmailToId` must be exact inverses.
  - Every `ownerof` and `machinePrograms` link must match its object, and every non-human
    creature and every program must have its link.
  - The `Creature` username and `Session` userId indexes must name matching objects, and
    every creature must be the target of its username index.
  - Any other link or index family is `Unmapped`. The manifest marks those 131 rows
    `blocked_link_authority`.
- The blocked total is now 556. That is larger, but it replaces an understated count.

## ADR 0017 legacy finance epoch

- The legacy finance subsystem exports as immutable `finance.legacy_record` capsules. They
  use the finance storage class, are append-only, are permanently retained, and carry a
  column-free document plus `record_family`, `legacy_key`, `currency`, `scale`,
  `entry_count`, and `content_digest`.
  - Thirteen JSON families: holds, pools, reservations, live debits, payouts, journal
    entries, project budgets, billing catalogs, quotes, the billing and market
    namespaces, VM billing, and per-lock `lockedTokens.{id}` roots.
  - The authoritative debt and withdrawable counters.
  - Twelve idempotency-marker families. These must survive, or a replayed request could
    apply twice after cutover.
- Derived counters (held, payout-held, spent, earned) and the four listing-link families
  are rebuilt and compared, never exported. Every legacy reconciliation invariant fails
  closed.
- Money must be an exact integer, because legacy readers truncate floats. Every marker must
  name an existing record, and a hold request marker must also match the hold's
  `requestHash`. Every listing link must name its record, party, and 20-digit timestamp.
  Unknown finance document roots are `Unmapped`, and a non-empty epoch requires an
  explicit currency and scale.
- Tests: `reconciled_finance_epoch_exports_authorities_and_drops_projections`,
  `finance_reconciliation_and_references_fail_closed` (13 rejection cases), and
  `finance_epoch_requires_explicit_currency_and_scale`. The storage-legacy suite has 21
  tests.
- Live PostgreSQL 16: the generated `aseman_finance.legacy_finance_records` table applies
  twice. UPDATE fails with SQLSTATE `55000` (immutability trigger), and a duplicate
  `(record_family, legacy_key)` fails with `23505`.
- Blocked rows went from 556 to 498. The remaining finance-adjacent rows are the VM runtime
  links, including the `VmBilling` listing link.

## ADR 0018 store memberships

- The `core.store_membership` schema, which nothing had implemented yet, is revised. The
  fields are `member_kind` (`creature`, `program`, or `remote_principal`), `member_ref`,
  the canonical `permissions` set, and `joined_at_micros` (`0` means unknown). The
  relationships are a required `store` and an optional `creature` or `program`.
  `(store, member_kind, member_ref)` is unique, and `role`, which legacy never had, is
  removed.
- Paired `hasaccess`/`onaccess` links become memberships owned by the store creator.
  - Permission tokens may appear in any order but must be known and must not repeat; the
    legacy literal `true` maps to the empty (deny-all) set.
  - Members resolve to a local creature (including machines), then a local program, and
    otherwise to a remote principal. A member whose origin the operator declares local
    but that has no row fails closed, as does a member without an origin.
  - One-sided pairs and a non-`true` `hasaccess` also fail closed.
  - Classifying a remote member requires `LegacyTransformEvidence::local_origins`.
- Tests: `memberships_keep_exact_permissions_and_typed_principals` and
  `membership_pairs_permissions_and_locality_fail_closed`. The storage-legacy suite has
  23 tests.
- `docs/operations/postgres-core-migration.md` now says that pre-cutover schema revisions
  fail transactionally on a database that applied an earlier revision. This was verified
  on PostgreSQL 16: after the committed `0001_core.sql` was applied, the revised migration
  failed on the missing `creature` column. The old `role`/`user` columns remained, and no
  new table was created. All live tests pass with the revised schema.

## ADR 0019 custodial private keys

- Legacy `/creatures/login` stores each user's PKCS#8 RSA private key in plaintext at
  `link::UserPrivateKey::{id}` and returns it on every email login. The DEV path accepts
  any email. The export verifies that each key belongs to an existing creature and derives
  that creature's registered public key; a mismatch, malformed key, or orphan fails closed.
  Key material never enters a capsule, digest, or error message, which a test proves
  byte-for-byte against the canonical encodings.
- The manifest marks the family `intentional_removal`. RL-019 owns deleting the custodial
  login. Cutover requires ADR 0009 proof-of-possession enrollment, or accepted
  verification-only status, for every affected identity.
- The test RSA keys are now generated once per test binary, which cut the storage-legacy
  suite (24 tests) from about 110s to about 12s.

## ADR 0020 operational raw keys and ADR 0021 guest KV

- `globalIdCounter` and `localIdCounter` must be exactly 8 big-endian bytes and at least the
  highest minted `{n}@global` / `{n}@{declared local origin}` object ID. Otherwise legacy
  would mint duplicates. They are verified and never exported.
- `chainCallback::*` is dead write-only state: nothing consumes or deletes it. It is
  shape-checked and dropped.
- A `god::*` superuser flag has no legacy writer, and any record fails closed as `raw.god`
  pending administrator review.
- Legacy guest `dbOp` pairs are committed as `link::{machineId}::{guestKey}`, not as raw
  keys. They become `guest.legacy_kv` capsules owned by the machine creature, bound for
  its isolated guest database's reserved `_aseman_legacy_kv` table (ADR 0021).
- Two legacy defects are recorded:
  - Guest `del` never removes a committed pair, because it deletes the unprefixed key.
  - `getByPrefix` never returns committed pairs, because it scans raw keys.
  The observable committed state, which `get` returns, is what migrates.
- The creature type registry, seeded at install and therefore present in every real
  snapshot, becomes global `core.creature_type` document capsules (ADR 0016 amendment).
  `CreatureTypeExists` flags must match registered specs exactly; the test is
  `creature_type_registry_exports_specs_and_verifies_flags`.
- Tests: `operational_raw_keys_are_verified_and_never_exported` and
  `guest_kv_moves_into_its_machine_creature_and_foreign_prefixes_fail`. The
  storage-legacy suite has 27 tests.

## Candidate review and ownership

- Heuristic candidate templates are classified mechanically:
  - Matches of reviewed families are `covered_by_reviewed_family`. This includes
    `MintApplied` (ADR 0017 finance marker, which must name an existing journal entry) and
    `AppletDb` (ADR 0021 `applet_db` guest namespace, owned by the creature, or by the
    program's machine creature).
  - Message strings, hash seeds, and process-local map keys are `not_a_storage_key`.
    Per-source evidence is recorded in the generator.
  - Every remaining family carries its owning phase.
- `docs/generated/legacy-transform-manifest.md` lists blocked rows by owning phase.
- The storage-legacy suite has 28 tests.

## ADR 0012 OpenRaft checkpoint

- `LegacyClusterCheckpoint::read_only` opens `<storage_root>/cluster/raft-db` read-only and
  reads `sm/state`. It requires exactly the `last_applied`, `membership`, and
  `shared_config` fields, and preserves the state verbatim as a canonical value with a
  domain-separated digest.
- `verify_legacy_cluster_replicas` requires identical digests across replicas before
  OpenRaft stops. A lagging or divergent replica fails closed.
- OpenRaft holds no application authority: replicated KV ops are already applied into the
  application RocksDB that the export reads. Membership is re-enrolled under ADR 0013.
  The `shared_config` operator knobs are returned for typed-configuration review (A103),
  and the checkpoint is retained only for the rollback window.
- Test: `openraft_checkpoint_is_read_only_digested_and_replica_checked`. The
  storage-legacy suite has 29 tests.

## ADR 0022 VM state (option 2: observed runtime is rebuilt by reconciliation)

- The evidence shows that legacy `install_program_bootstrap` never relaunches instances;
  launch parameters and resources are never persisted, and instance links can go stale.
  Observed runtime is therefore not exported.
  - Covered families: instance, status, started-at, owner, container, terminal, build,
    proxy correlation, and `Modal*` handles.
  - `legacy_vmm_handoff_inventory` shape-checks each record and reports per-family
    counts, and no `core.workload` is fabricated.
  - The data stays in the wrapped legacy provider for the native-legacy VMM until
    RL-013. P5 reconciliation adopts or stops each inventoried instance, and P6 adopts or
    releases each `ModalVolume`.
- Durable intent migrates:
  - `core.gateway_route`; the reverse link and username alias are verified, and the
    pinned observed `vmId` is dropped.
  - `core.program_alarm`: exact millisecond-to-microsecond conversion, entity defaults
    to `main` as in legacy replay, and a non-program subject fails closed.
  - `core.vm_resource_store` and `core.vm_resource_entity` (document plus data-file
    evidence).
  - `core.entity_config` (proxy entity configuration).
  - `core.entity_artifact` (primary and downloadable artifacts, with copy evidence).
- Artifacts use `LegacyTransformEvidence::path_artifacts`: each exact legacy path is
  either `Present` with copy evidence or `AttestedAbsent`, because legacy deletes remove
  files but keep records. A path with neither fails closed.
- `vmDistribution` is an intentional removal (ADR 0012). The `VmBilling` flag must match
  its payment record exactly. `vmOwnedStore` and `vmEntityType` are verified.
- The plan now records the obligations: the Phase 3 gate carve-out, P5 adoption, P6
  Modal adoption, and the RL-005/RL-013 ordering in the removal ledger.
- Tests (the storage-legacy suite has 35 in total):
  - `observed_vm_runtime_is_inventoried_for_the_vmm_and_never_exported`
  - `vm_billing_flag_must_match_its_payment_record`
  - `gateway_routes_and_alarms_migrate_as_durable_intent`
  - `gateway_route_and_alarm_divergence_fails_closed`
  - `vm_resources_configs_and_artifacts_migrate_with_evidence`
  - `vm_resource_divergence_and_missing_evidence_fail_closed`

## ADR 0016 slice verification

- `cargo xtask fast`: generators up to date, characterization, unit, and
  `clippy -D warnings`. The storage-legacy suite has 18 tests, including stale, unequal,
  missing, foreign-path, orphaned, unreviewed, non-object, and out-of-range document
  rejection.
- `cargo xtask full`: passes. `caspar-node` binaries build, its library tests pass
  (380), and `casparctl` tests pass (35). The legacy node and CLI were not modified.
- A disposable PostgreSQL 16 (`postgres:16-alpine`) run with `ASEMAN_TEST_POSTGRES_URL`
  applied both migrations twice and passed the existing conformance and isolation tests.
  It also passed `live_document_capsules`: a metadata capsule round-trips byte-for-byte,
  its table has no `document` column, a second document for the same subject returns a
  conflict, a dangling subject is rejected by the foreign key, and a filter on `document`
  fails closed.
- Legacy verification caught a real hazard: a JSON `u64` above `i64::MAX` would have
  become a lossy float. Such numbers now fail closed.
- `aseman-storage-legacy` is split by responsibility: `graph`, `export`, `objects`,
  `timeseries`, `documents`, `capsule`, and `tests`. The public API is unchanged, and
  `objects.rs` (641 lines, eight typed families) is the largest source module.

## Acceptance (A308)

A308 is **ACCEPTED**. Every A004 row, every heuristic candidate template, every typed
object family, both QuestDB tables, all eight Hashgraph families, and the OpenRaft store
carry a reviewed, non-blocked disposition (ADRs 0016–0025). The generated manifest
records zero blocked rows, and the Phase 3 characterization test asserts that invariant.

The migration runner must supply this explicit evidence; each missing item fails closed:
- `LegacyFinanceConfig`: currency and scale.
- `local_origins`: the ID origins owned by this installation.
- `file_artifacts`: evidence for legacy `File` rows.
- `path_artifacts`: copy evidence or attested absence for entity artifacts and resource
  entity files.
- `secret_master_key`: the legacy `node-secret-key`, used only to authenticate
  ciphertext.

The runner also composes the separate read-only readers: QuestDB build-log and signal
rows, `LegacyClusterCheckpoint` (OpenRaft), `LegacyHashgraphCheckpoint`, and the VMM
handoff inventory.

Legacy defects found during the review are tracked in `docs/migration/legacy-defects.md`.
P3-06 (A309 dual write, semantic comparison, cutover, and rollback) is now unblocked.

## ADR 0023–0025 slices

- ADR 0023: secrets migrate as ciphertext authenticated under the operator-supplied master
  key, with a redacted `Debug` for the key, and grants migrate with exact reverse-index
  mirroring. Login grants are shape-checked and dropped.
- ADR 0024: bridge grants migrate by token digest, with topic claims. `NodeIpToHost` has
  no writer and fails closed.
- ADR 0025: the Hashgraph store is consensus-provider state, strictly classified, with a
  block-digest checkpoint.
- The storage-legacy suite has 39 tests.

## Rollback

The bridge is read-only and additive. Its rollback is removal of the unused module and
export artifacts. Once a future backfill starts, the source remains authoritative and
immutable checkpoints are retained until P3-06 comparison and rollback gates pass.
