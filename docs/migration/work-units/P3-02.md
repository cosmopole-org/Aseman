# P3-02 native PostgreSQL core work record

## Requirement and artifacts

P3-02 implements A305 under ADR 0005 and ADR 0006. RL-005 owns replacement and
deletion. This work adds a target provider but does not change current storage authority
and does not authorize removal of RocksDB, QuestDB, physical keys, or node adapters.

## Implemented

- Generated `aseman_core` physical mapping and transactional DDL for all twenty core
  kinds, including explicit logical-to-physical names for envelope-field collisions.
- Native typed columns, live-row required-field checks, revision-chain checks, owner
  checks, foreign keys with reviewed delete policies, partial unique indexes, and stable
  range indexes. No JSONB entity bucket or shared guest payload table exists.
- Trusted `guest_database_bindings` and `guest_schema_definitions` catalog tables; guest
  records themselves remain assigned to per-creature databases in P3-03.
- PostgreSQL capsule repository with integrity verification, typed extraction,
  parameterized typed queries, bounded results, atomic revision compare-and-set,
  canonical retry idempotency, tombstones, and exact capability reporting.
- Version-1 capsule-storage gRPC contract, generated client/server bindings, module
  control lifecycle, deadlines, cancellation, bounds, structured errors, and protected
  secret-file configuration.
- Reusable A310 harness execution against a disposable PostgreSQL 16 database plus a
  real gRPC boundary test. The live test found and drove fixes for reserved identifiers,
  envelope/body column collisions, and sync-driver runtime composition.

## Migration and rollback

The provider is additive and isolated from the legacy authority. Apply and rollback
procedure is recorded in `docs/operations/postgres-core-migration.md`. Rollback routes
to the unchanged legacy binding and preserves the PostgreSQL schema for comparison.
RL-005 remains open until P3-05/P3-06 replacement and deletion evidence passes.

## Activation boundary

The provider executable requires database egress and a protected connection secret.
The current local module launcher supports only zero host permissions and therefore
fails closed instead of pretending to isolate this process. A sandbox launcher with an
exact permission receipt is required before production activation; this does not weaken
the accepted native schema/repository evidence.
