# P9-01 the bootstrap workflow

## What it replaces

A giant imperative installer script, whose defining property was that running it twice
could destroy a working deployment.

## The rule

**A stage that has already succeeded is never run again.** Recording a finished stage
is an error, not a no-op, so an installer cannot quietly re-do work an operator has
already relied on.

Resuming is therefore trivial: ask what is next. An interrupted bootstrap re-entered
from the beginning skips everything it already did, because the progress file says so.

## The stages

Preflight, topology, artifacts, identity, schema, services, health — each depending on
every stage before it. A stage cannot jump ahead: starting services before the schema
exists is not a shortcut, and is refused.

## Rollback that cannot destroy data

The schema stage is the line.

- **Before it**, a failed stage is undone: everything it created, the bootstrap itself
  created.
- **At and after it**, a failed stage is rolled *forward* by re-running it. Undoing
  would drop a database or stop a running node — which is precisely the "clean up after
  yourself" behavior that loses people's data.

## Preflight reports, it does not gatekeep on taste

A non-fatal finding is reported and the bootstrap continues. A host without `/dev/kvm`
runs containers perfectly well; refusing to install because it cannot *also* run
microVMs would be wrong. Only a fatal finding — no cgroup v2, for instance — stops it.

## Verification

Seven cases: a clean host runs every stage in order; an interrupted bootstrap resumes
where it stopped; a finished stage never runs again; a stage cannot jump ahead; a failed
stage is retried rather than skipped and its failure clears on success; rollback is
`Undo` before the schema and `RollForward` at and after it; and a host that cannot run
microVMs still passes preflight.

## A constraint worth recording

The round-trip of the progress file through JSON is *not* tested in the domain, because
`aseman-domain` may depend only on serde, thiserror, and uuid — not `serde_json`, even
as a dev-dependency, since the architecture check inspects dev-dependencies too. The
property belongs with the CLI that writes the file. Weakening the architecture rule to
make one test convenient would have been the wrong trade.
