# P6-03 worker enroll, cordon, drain, and loss

## What this is

`modules/vmm-backend/nomad/src/workers.rs` is the operator's view of the worker pool:
list, cordon, uncordon, drain, cancel a drain, and ask whether a drain has finished.

It is a separate type from the backend, holding a separate Nomad token, because the
component that runs workloads must not be able to cordon the cluster it runs them on.
The backend's token has no `node-write` capability (A602); these actions need an
operator token. Holding a `NomadBackend` gives you no way to reach any of this.

Enrollment itself is Nomad's: a client that joins the cluster with the operator's
certificates appears in `list()` and the scheduler starts using it. Aseman adds nothing
to that, and must not — a node that enrolled workers itself would be a second scheduler.

## Behavior worth stating

**A cordon does not disturb what already runs.** It stops placement, which is the first
half of taking a machine out of service: it stops the bleeding while an operator decides
whether to drain or to fix it in place.

**A cancelled drain does not uncordon.** Nomad's cancel clears the drain; Aseman leaves
the worker ineligible. Returning a suspect machine to rotation is a decision an operator
makes out loud, with `uncordon`, not a side effect of changing their mind about a drain.

**Identity is untouched by all of it.** Draining a worker, losing one, or restarting a
workload elsewhere changes which machine runs it and nothing else. The workload keeps
its ID and its generation, and the Aseman node keeps its ID and signing-key lineage
(ADR 0013).

**A lost workload is reported as lost.** The backend says what is true, not what was
asked for. Reconciliation then issues `Restart`, which is a start at the same
generation — no new workload is invented to replace a dead one (A503, ADR 0022).

## Verification

Both cases run against the real cluster, not a double.

| Requirement | Evidence |
|---|---|
| Cordon stops placement and leaves running work alone | `a_worker_is_cordoned_drained_and_returned_without_touching_identity`: after the cordon the worker is ineligible and the workload is still `Running` |
| Drain moves work off | the same test waits for the worker to report drained, then observes the workload no longer running |
| A cancelled drain does not return the worker to service | the test asserts the worker is still ineligible after `cancel_drain` |
| Identity survives | the workload's ID and generation are compared before the cordon and after the return |
| A dead workload is observed and restarted as itself | `a_lost_workload_is_observed_and_restarted_as_itself` removes the container out from under Nomad — what a worker's kernel does on an out-of-memory kill — then asserts the observation stops being `Running`, that `Restart` brings it back, and that the ID and generation are unchanged |

The cordon test restores the worker in a `Drop` guard, so a panic cannot leave an
operator with a cordoned machine and no idea why. Both tests purge their jobs.

## Open, and owned

- **Losing a whole control replica** is P6-03A, which is delivered: the singleton work
  moves to another replica under a fenced lease.
- **Volume behavior when work moves** is P6-06 (ADR 0011): a stateful workload does not
  move unless every attached volume declares a compatible path.
- **Chaos fixtures** covering partition and clock skew are P6-06's.
