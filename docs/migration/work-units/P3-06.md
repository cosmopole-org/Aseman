# P3-06 dual write, semantic comparison, cutover, and rollback

## Requirement and ownership

P3-06 implements A309 (the dual-write, read-compare, cutover, and rollback parts of the
protocol) under ADRs 0005, 0006, 0007, and 0016–0025. RL-005 owns the legacy storage
path, and its deletion stays gated on a production cutover plus its deletion gate.

## Delivered (A309 ACCEPTED)

- **Domain** (`aseman-domain::storage_migration`, pure):
  - The ten-step state machine with phase guards and monotonically increasing binding
    generations. Rollback raises the generation to fence stale writers, and a lost
    shadow write blocks the delta before cutover and forbids rollback after it.
  - `compare_records`: counts per kind, identities, semantic digests, and dangling
    references.
- **Ports:** `MigrationStateStore` (compare-and-swap), `MigrationRecordSource`, and
  `CanonicalRecordWriter`. Writers must fence old generations transactionally.
- **Application:** `StorageMigrationService`, which drives the steps against durable
  state, and `DualWriteRouter`, which writes the authority first, then shadows the
  write and records failures durably.
- **Contracts:**
  - `semantic_digest` covers what a record means and excludes the revision chain, so
    re-applied revisions still compare equal (ADR 0005).
  - `plan_delta` produces inserts, chained replacements, and tombstone revisions.
- **PostgreSQL provider:**
  - Writes, reads, queries, and snapshots every storage-class table the export emits.
    Previously only the core tables had a writer.
  - Enforces class checks and refuses updates of append-only kinds.
  - `put_fenced` runs the generation check in the same transaction as the write.
    `0003_migration_fence.sql` holds the fence, which only increases.
  - `snapshot_all` feeds the comparison.
  - The guest legacy KV importer writes into the creature's own database, into the
    reserved `_aseman_legacy_kv` table, with an owner check and idempotent replay.
- **Proof:** `tests/migration` runs the whole chain live on PostgreSQL 16: legacy
  snapshot, export, import, guest import, verify, a blocked delta, the applied delta,
  fenced cutover, and rollback.
- **Docs:** `contracts/migration/protocol.md` and
  `docs/operations/storage-migration-runbook.md`.

## Node rewiring (legacy provider wrap)

- `aseman-storage-legacy` now owns every legacy storage client:
  - `LegacyKvStore` with `RocksDbKvStore`: exact prefix scans by seek, atomic batches.
  - The process-wide RocksDB tuning and block cache (`tuning`).
  - `QuestDbTimeSeries`: the startup table repair, tag-validated signal SQL, and
    build logs. It uses the same `LegacySignalRow`/`LegacyBuildLogRow` types as the
    migration export.
- The node's core path names no RocksDB or QuestDB types: `KvDb` is
  `Arc<dyn LegacyKvStore>`, and `ts_db()` left the `IStorage` port. The rewired paths
  are `trx.rs`, `drivers/storage.rs`, cluster KV apply, telemetry, and `scan_vmdb`.
- Remaining in-node RocksDB users are Phase 3 gate exceptions with owners: the OpenRaft
  store (`drivers/cluster/store.rs`, RL-012 / ADR 0012) and the Hashgraph store
  (`hashgraph/rocks_store.rs`, RL-011 / ADR 0025, which moves into
  `modules/consensus/hashgraph` in P8). Both use the provider's shared tuning.
- Behavior is unchanged, including LD-10 (a swallowed commit failure), which is
  preserved as characterized.

- **Inventory:** `generate_legacy_data_inventory.py` maps the shared `access_link_key`

- **LD-12 repair:** `audit_legacy_memberships` and `repair_legacy_memberships` in

  - Test: `membership_audit_repairs_ld12_residue_only_under_the_approved_digest`. After

- **Verification (2026-09-21):** `cargo test -p aseman-node --lib` passed 382 tests.
  `cargo xtask fast` passed with `ASEMAN_TEST_POSTGRES_URL` set.

## Provider selection and routing (ADR 0026)

- **Config:** `aseman-config::CoreStorageConfig` (`ASEMAN_CORE_STORAGE_PROVIDER` =
  `legacy` by default or `postgres`, which needs `ASEMAN_DATABASE_URL_SECRET`;
  `ASEMAN_CORE_BINDING_GENERATION`). The node migrates PostgreSQL and installs the
  factory before any state action (`install_core_storage`).
- **Unit of work:** `aseman-storage-postgres::unit_of_work` runs one transaction per
  action on a pooled connection. Each write runs under a savepoint and is fenced at the
  generation; dropping a unit rolls it back. The repository's read and write paths run
  on any client (`get_on`, `query_on`, `write_prepared`). `FencedCapsuleStore` fences
  single writes.
- **Routing:** `core_storage::run_action` opens the unit, runs the action, commits
  PostgreSQL then legacy, and runs the registered compensations if the legacy commit
  fails. The orchestrator's state entry points share it (`run_trx_closure`,
  `run_state_closure`), and a failed action is distinguished from a storage failure.
- **Routers:** one per family, over private legacy adapters. The call sites use the
  routers, and the aggregate `LegacyStorePorts` is gone.
- **Balances:** legacy balances are the `balance` column alone, so a creature whose
  identity is on PostgreSQL has no shell object on legacy.
- **Revive fix:** `next_revision` always yields a live revision, so a deleted record
  written again continues its chain on capsules. Every conformance suite checks
  delete-then-recreate, and `store_access` adds membership re-join.
- **Tests:** `live_units_of_work_are_atomic_isolated_and_fenced` and
  `live_actions_route_core_families_to_postgres_with_ordered_commits` (the identity on
  PostgreSQL and the balance on legacy in one action, a refused action rolled back on
  both, compensation after a failed legacy commit).

## Creature strangler (RL-004)

- **Ports:** `CreatureDirectory` (identity) and `CreatureBalances` (balance: `open`,
  `balance`, `set_balance`, `close`), plus the
  `aseman-domain::creature` values and the shared `legacy_page` window. The balance is
  separate because the target model keeps it in `finance.wallet`.
- **Use cases:** `aseman-application::creature` (create, get, list, update, delete,
  getByUsername, find). The rules and error texts are the legacy ones, except for
  LD-13.
- **Legacy adapter:** `LegacyCreatures` (node) keeps the `Creature` object, the
  `username` index, and the `balance` column exactly.
- **Capsule adapter:** `aseman-capsule::creature` writes what the A308
  export writes (`core.user` for humans, `core.creature`, `finance.wallet`,
  `core.legacy_identity`) in one transaction.
  - PostgreSQL gained `put_all` / `put_all_fenced` (up to 64 capsules; it advertises
    `transactions.multi_capsule`). `CapsuleStore` gained `put_all`.
  - Listing pages by keyset, and re-sorts by bytes wherever legacy order matters.
- **Conformance:** `aseman_ports::conformance::creature_directory` (feature
  `conformance`) runs on both adapters: `legacy_creatures_pass_the_directory_conformance_suite`
  in the node, and `live_creature_ports_pass_conformance_on_capsules` live on
  PostgreSQL. The live test also proves that `put_all` rolls back a partial write.
- **Rewired:** `/creatures/create`, `get`, `list`, `update`, `delete`, `meta`,
  `getByUsername`, `find`; `/machines/list`; the VM creature host calls (LD-14
  mitigation); the driver's username route lookup.
- **Documented differences after cutover:**
  - Public keys are stored canonically (contracts `legacy_keys`), so a non-standard
    PEM spelling reads back as the standard LF PEM, and a non-RSA key is refused.
  - A machine must be owned by a human user, as the A308 export requires.
  - `/creatures/create` resolves the type's opening balance before the username
    check, so a request that is wrong in both ways reports the unknown type first.
- **Export fix (A308):** a human without an email was exported with `email = ""`.
  Because `uq_users_email` is unique, the second such human would have made the import
  conflict. An absent email is now omitted (NULL). The live test creates email-less
  humans side by side.
- **Balances:** every balance read and write goes through `CreatureBalances` via the
  legacy `Account` helper. That covers `/creatures/transfer`, `mint`, `lockToken`,
  `consumeLock`, the 13 balance sites in `creature/finance.rs`, and the finance
  reconciliation audit. A write-back sets only the `balance` column; the old code
  re-pushed the whole record.
  - LD-13, finance: the `id.is_empty()` checks at these sites never fired. A credit to
    a missing creature re-pushed the record and created a partial Creature. Now the
    site's existing "not found" error fires, a write-back to a missing creature fails,
    and the audit reports a withdrawable counter that has no creature.
  - Test: `accounts_write_only_the_balance_and_never_create_ghost_creatures`.
- **Identity reads:** the remaining `Creature::pull` reads (VM host calls, proxy, chain,
  program actions, store signal, login, creature signal) and the `type`/`username`
  column reads in the guard, security driver, and signaler use the directory.
  `creature_or_empty` keeps legacy `pull` semantics: a missing creature reads as an
  empty record with its id.
  - LD-13, login: a stale `UserEmailToId` link is now dropped as the code intended.
- **Still direct:** finance ledger state (journals, withdrawable, debt, holds, payout
  counters), the creature type registry, metadata documents, sessions, email and
  private-key links, and the `ownerof` / `machinePrograms` relations. These belong to
  the finance-ledger, identity, and program slices.

## Creature metadata (RL-004)

- **Port:** `CreatureMetadata` (`MetadataKind::Creature` / `User`). Documents cross it
  as JSON object text; paths are legacy dotted paths under `metadata`.
- **Shared conversion:** `aseman-contracts::legacy_documents` (JSON to capsule value
  and back, digest, the ADR 0016 document fields, path lookup). The A308 export and
  the capsule adapter both use it.
- **Adapters:** the legacy adapter keeps the `json::CreatMeta` / `json::UserMeta`
  splats, clearing the tree before a replace so no stale child splat survives. The
  capsule adapter writes `core.creature_metadata` / `core.user_metadata`, revives a
  tombstone as the next revision, and returns only objects at a path, as legacy
  `get_json` does.
- **Conformance:** `aseman_ports::conformance::creature_metadata` on both adapters.
  The node test, and the live PostgreSQL test with a key unique in the target
  schema.
- **Rewired:** `/creatures/create`, `delete`, `meta`, the user extender fields
  (`getByUsername`, `find`), and the `/machines/list` profile.
- **Owner links (LD-16):** the legacy adapter derives `ownerof` on create, update, and
  delete. The pre-export repair (`repair_legacy_memberships`, audit digest v2) removes
  dangling and stale links and rebuilds missing ones.
- **Type registry:** `CreatureTypes` port (`Json::CreatureType` + `CreatureTypeExists`
  on legacy, `core.creature_type` on capsules), with conformance on both adapters.
  Built-in registration, the legacy human-balance migration, `resolve_initial_balance`,
  and `/creatures/types` use it.
- **Identity credentials** (sessions, email login links, custodial keys, secrets, login
  grants) stay legacy-authoritative until the P4 obligations of ADRs 0019/0023 are met
  (ADR 0026).

## Store records and metadata (RL-004)

- **Ports:** `StoreDirectory` gained `stores`, `create_store` (with the creator),
  `update_store`, and `delete_store`, and `StoreRecord` carries every legacy field.
  A new `StoreMetadata` port (deep merge) covers `StoreMeta`. Conformance runs on both
  adapters (`store_directory`).
- **Adapters:** `LegacyStores` (node, trx only; `LegacyStorePorts` delegates to it)
  keeps the `Store` object, the `creatorof` link, and `StoreMeta`. The capsule adapter
  writes `core.store` owned by its creator, with an optional `parent` relationship, a
  legacy identity, and `core.store_metadata`. The capsule document families share
  one `DocumentFamily` helper, and program metadata uses it too.
- **Rewired:** the VM store host calls (create, update, delete, get, list), federated
  store update and delete (LD-20), the VM driver's store reads, the finance
  project-budget check, and member removal on creature delete.
- **Audit:** stores whose parent is missing or is themselves are reported for an
  operator (`DanglingStoreParent`).

- **Adapters:** `LegacyPrograms` (node; `Json::VmResourceStore` `core`/`metadata` plus

## Gateway routes (RL-004)

- **Port:** `GatewayRoutes` (route, reverse index, username alias) with the
  `aseman-domain::gateway` value, and conformance on both adapters.
- **Adapters:** `LegacyGatewayRoutes` (node; `vmHttpRoute`, `vmHttpRouteFor`,
  `vmHttpRouteUser` through `aseman_contracts::legacy_gateway`) and
  `aseman-capsule::gateway` (`core.gateway_route` scoped to its creature;
  the reverse index and aliases are derived by query, and an entity that moved
  resolves to its most recent route).
- **Pinned instances:** a pinned VM id is observed runtime (ADR 0022). The legacy
  provider keeps it; the capsule provider does not persist it, so a pinned route
  becomes unpinned after cutover, exactly as migration already treats it.
- **Rewired:** `register_gateway_route` (deploy, entity deploy, cluster propagation)
  and the driver's route lookup. Cluster propagation now writes its program through
  `ProgramDirectory`, so the `machinePrograms` link is written with it (LD-17).

## Program family (RL-004)

- **Ports:** `ProgramDirectory` (records and the `machinePrograms` relation) and
  `ProgramMetadata` (deep merge, as legacy `put_json(.., merge = true)`), with the
  `aseman-domain::program` value and conformance on both adapters.
- **Use cases:** `aseman-application::program` (`CreateProgram`,
  `UpdateProgramPath`, `DeleteProgram`). Only the owner of the machine may change a
  program (LD-18).
- **Adapters:** `LegacyPrograms` (node; `Program` object, derived link, `ProgMeta`) and
  `aseman-capsule::program` (`core.program` scoped to the machine,
  `core.program_metadata`, legacy identities). The shared capsule helpers moved to
  `support.rs`.
- **Rewired:** `/programs/create`, `update`, `delete`, `list`, `deploy`, the existence
  checks, `/machines/listProgramMachines`, program bootstrap, and the VM program host
  calls (create, delete, get, list, listByMachine, update, deployEntity). The no-op
  `machinesCount` pushes are gone, since `Creature::push` never wrote that column.
  `resolve_program_owner_machine` no longer scans links in reverse, because the link
  always names `machineId`.
- **Schema fix (A304):** `core.program.machine_id` was unique, which rejects the
  migration of a machine with several programs (legacy allows them). The logical
  schema drops the unique index, and `0004_program_machine_not_unique.sql` replaces
  it with a plain index on databases already migrated. The live test creates two
  programs per machine.
- **LD-17:** deletes really delete, deploys and updates refuse missing programs, and
  the pre-export repair handles program links (audit v2).
- **Alarms:** `ProgramAlarms` port (`vmAlarm*` links on legacy, `core.program_alarm`
  related to the program and its store on capsules), with conformance on both
  adapters. Program bootstrap replays through it, and `plantTrigger` sets it and clears
  only its own alarm (LD-19).
- **Remaining program state:** entities and entity artifacts (`core.entity`,
  `core.entity_artifact`). Their bytes go through the blob store (ADR 0027, below). VM
  runtime keys stay legacy (ADRs 0022/0026).

## File bytes (ADR 0027)

- **Port:** `BlobStore` (`put_blob`, `blob`, `has_blob`, `delete_blob`, `local_path`)
  over the domain's `BlobEvidence` and `valid_blob_key`, with a conformance suite.
- **Provider:** `drivers/blob_store.rs` `StorageRootBlobStore`: keys are paths relative
  to the node storage root, which is where legacy kept the bytes, so no bytes move at
  cutover. It passes the conformance suite.
- **Callers moved:** entity deploys (program actions, VM host calls, cluster artifact
  replication) write through `put_entity_file`. Public uploads and downloads
  (`/storage/*`, `creatures/storageUpload`) use the `public-files` folder key.
- **Deleted:** the `IFile` trait, its `drivers/file.rs` driver, and their pass-through
  handles (`ITools::file`, the VMM and federation fields). With no callers left they
  were a redundant layer. The rollback is unchanged, because the bytes and paths are the
  same.
- **LD-25:** deploy file names can no longer escape the entity folder.

## Entities (RL-004)

- **Port:** `EntityDirectory`, covering entity records, primary and downloadable files as
  blob keys, the programs with a deployed entity, and the entity configuration.
  Conformance runs on both adapters: `LegacyEntities` in the node, and
  `CapsuleEntityPorts` on live PostgreSQL.
- **Legacy encodings kept:** the `Entity` object, and `vmEntityPath` /
  `vmEntityDownloadable` holding the local path, which the adapter maps to and from
  blob keys. The `vmEntityType` link is derived and kept equal to the entity's type,
  as the A308 export requires. The capsule side stores no such link. Both adapters
  refuse an entity without a program and a file or config without an entity.
- **One deploy write:** `RecordEntityDeployment` (`aseman-application::program`)
  writes the entity, its files, and its configuration for `/programs/deploy`, the VM
  deploy host call, proxy deploys, and the cluster applier. Before this change, each
  path wrote the keys by hand.
- **Readers moved:** the VM execution-target resolver, `/programs/runEntity`,
  `stopEntity`, `destroyEntityVm`, `listEntityVms`, `downloadEntity`, the standalone
  VM reaper, proxy forwarding, and the startup listener restore. The four copies of
  the resolver are now one function.
- **Known gap (unchanged):** the cluster deploy command does not carry `downloadable`,
  so replicas do not serve `/programs/downloadEntity` for a distributed deploy.

## VM resource entities (RL-004)

- **Port:** `VmResourceEntities` over `ResourceEntityRef` (store, type, id). The domain
  owns the identity rules (`is_valid`, `legacy_id`) and the data blob key
  `vm_stores/{store}/{type}/{id}.json`, which is where legacy kept the file. Conformance
  runs on both adapters: `LegacyEntities` (payload and meta documents, `meta.path` as
  the local path) in the node, and `CapsuleEntityPorts` (`core.vm_resource_entity`) on
  live PostgreSQL.
- **Use cases:** `PutResourceEntity` and `DeleteResourceEntity` write or remove the data
  blob together with the record. The `createResourceEntity` / `deleteResourceEntity`
  host calls use them and do no file I/O of their own.
- **LD-26:** path traversal, `::` keys, orphan entities, and deletes that did nothing
  are fixed.

## Transaction atomicity (ADR 0026 prerequisite)

- LD-10: `ITrx::commit` returns write errors; a failed batch replicates nothing.
- LD-15: secured actions and the VM signal host call discard a failed action's writes,
  as the Go original did, and report a failed commit as the action's error
  (`ICore::modify_state_securly_checked`).
- Test: `a_failed_commit_is_reported`.

## Remaining

- **Deletion:** removing the legacy storage path requires a real deployment cutover and
  the RL-005 deletion gate (AGENTS: never delete before both gates pass).
- **CLI:** the `asemanctl storage migration …` operator surface is delivered by P9-01.
- **Strangler:** complete for core families. The storage-access inventory shows no
  direct core-family access outside the port adapters. The direct accesses that remain
  belong to ADR 0026 legacy families: finance (P8), identity credentials and sessions
  (P4), VMM observed runtime (ADR 0022), id allocation (P4), and chains (P8).
- **Signature verification:** `ISecurity::auth_with_signature` read the caller's public
  key from the legacy `obj::Creature` column (`ITrx::get_pub_key`). After cutover, a
  creature created on PostgreSQL could not have authenticated. It now reads the
  creature record through `CreatureDirectory`, once, for both the key and the type,
  and is covered by a test. `ITrx::get_pub_key`, the unused `ITrx::get_pri_key`, and
  `Security`'s unused storage and signaler handles are removed.
- **Cutover blockers:** LD-14 and LD-24 (P4 guest gateway).
