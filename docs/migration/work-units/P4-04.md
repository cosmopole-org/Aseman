# P4-04 signed workload authentication and trusted guest database resolution

## Requirement and ownership

P4-04 implements A405 and the guest gateway. The resolution chain is workload, then
program, then creature, then binding, and it is never caller-selected. Moving the guest
host calls behind the gateway fixes LD-14 and LD-24 and unblocks the Phase 3 cutover.
RL-006 owns the replacement of the legacy guest data path.

## Delivered (step 1: the gateway)

- **Domain:**
  - `guest`: legacy KV operations, namespaces, limits, and outcomes.
  - `BindingStatus` on bindings.
  - `Generation::from_stored`.
- **Ports:**
  - `CreatureDatabaseBindings::record_binding`, which never moves generations backwards.
  - `GuestKv`.
  - Conformance suites for both.
- **Application** (`aseman-application::guest`):
  - `GuestGateway` runs from an authenticated workload through resolution to an active
    binding, then policy (`same_creature`), then the operation.
  - `ServeSignedGuestRequest` puts A401 authentication in front of it.
  - Adversarial tests: cross-creature isolation, non-workload subjects, a signed action
    mismatch, unknown and deleted workloads, disabled and missing bindings, replayed,
    forged, and impersonating proofs, and an unavailable directory.
- **Adapters:**
  - `CapsuleWorkloads` implements `WorkloadRepository` and `CreatureDatabaseBindings`
    over `core.workload` and `core.guest_database_binding`. A program of another
    creature fails closed.
  - `PostgresGuestKv` runs sealed capsule revisions and tombstones in the creature's
    role. It shares the reserved table DDL with the importer.
- **Live PostgreSQL:** binding and KV conformance, plus an end-to-end gateway test with
  the registry policy: isolation, a tampered record refusing to route, and a crossed
  program failing closed.

## Delivered (step 2, part 1: host-call caller identity)

- **LD-27 fixed:** host-call identity is read only from the packet the runtime or
  docker gateway stamps. The docker gateway stamps its verified identity at packet level
  and refuses unidentified containers. Secret reads, shell actions as self, and `dbOp`
  namespacing can no longer be pointed at another VM's creature by a guest-supplied
  `vmId`.

## Delivered (step 2, part 2: LD-24, ADR 0028)

- `guest_state` is the one implementation of `putJson`/`getJson`/`getByPrefix`/
  `delKey`/`getLink`, confined to a node-supplied creature. The unified host call passes
  the packet creature, the runtime JSON transactions pass their VM context's creature,
  and `vm_callback` refuses the calls. The unconfined arms of
  `handle_micro_host_action` are deleted.
- A node test shows that node documents, custodial keys, and other creatures' state are
  unreachable, that listing and whole-document deletes stay inside the creature, and
  that callers without an identity are refused.
- Export: `GuestDoc` records become `json` rows of the creature's guest database, one
  row per physical record. A creature that is not local fails closed. The namespace is
  in the table contract, the importer, and the DDL, which upgrades old tables
  idempotently.

## Delivered (step 2, part 3: documents in the gateway)

- `legacy_json_index_writes` (contracts) plans exactly the records `index_json` writes.
- The domain has `PutJson`/`GetJson`/`DeleteJson`/`ListJson` operations and
  `Document`/`Keys` outcomes.
- `PostgresGuestKv` serves them over `json` rows as capsule revisions, planning each
  write against a snapshot of the stored rows.
- The `GuestKv` conformance suite covers the document semantics (records, merge,
  replace, subtree and whole-document delete, byte-order listing, object root), with the
  same observable results as the node's legacy test. It passes on live PostgreSQL.

## Delivered (step 3: LD-14 and guest data on PostgreSQL)

- **Identity-less paths closed:**
  - Runtimes send lifecycle, HTTP, and proof calls through the unified host call
    (wasm, JavaScript). Elpian wraps every guest call in the node-stamped envelope
    instead of passing the guest's raw packet.
  - The dispatcher refuses unknown operations instead of forwarding them.
  - `protocolApi` is refused, and `node.protocol.call` is `never`.
  - `vm_callback` serves only runtime and node events: output and logs, a runtime's own
    trigger and signal, and node terminations.
- **Every host call is authorized** as its A402 action (`node/src/shell/authority.rs`,
  see P4-05). A guest-created creature belongs to the guest's owner and cannot be
  funded. LD-14 is fixed.
- **Guest data on PostgreSQL** (`shell/api/model/guest_data.rs`, ADR 0021/0028): with
  the core provider on PostgreSQL, all three guest data paths (runtime `dbOp`,
  host-function `dbOp`, confined documents and links) are served from the creature's
  active binding through the guest proxy, in the legacy response shapes. A creature
  without an active binding is refused. Configuration: `ASEMAN_GUEST_PROXY_*`. Tested
  live against a real creature database.
