# P5-07 VM logs come from the VMM

## Why

P5-06 deleted the host bridge that wrote VM output into the node's legacy build-log
table, but `/machines/readVmLogs` still read that table. Nothing wrote it any more, so
the endpoint answered every request with an empty page — a dead path the generated call
graph could not see, because it still looked for the deleted `IVmm` method names.

## Changed

| Change | Why |
|---|---|
| `/machines/readVmLogs` reads the workload's A501 `logs` stream through the node's VMM client | A workload's logs are its VMM's (ADR 0030). The endpoint keeps the legacy `BuildPacket` shape, with the VMM's log sequence as the cursor |
| The endpoint refuses a VM it cannot find an instance link for | The old "build logs are readable by any authenticated user" branch existed only because a node-wide build stream had no owner. It has one now |
| `IStorage::log_vm` and `IStorage::read_vm_logs` deleted, with the driver and its test doubles | The node writes and reads no VM logs. The legacy rows stay in the legacy store for the Phase 3 export (`transform_legacy_build_log`) |
| The backend registers a build-on-deploy workload before building its image, and retries a failed build on next use (`Instance::build_pending`) | The build's output needs an owner to be attributed to, and a build that failed must not be skipped forever |
| The docker plugin emits build output under the packet's `vmId` | It emitted under a node-wide `"main"` stream the backend dropped (LD-30) |
| `scripts/generate_current_call_graph.py` reads the VMM client surface from `RemoteWorkloads` itself | The generator pinned the deleted `IVmm` method names, so every VM operation silently disappeared from the inventory. Reading the surface from the client keeps it honest when the client changes |

## Verification

| Requirement | Evidence |
|---|---|
| Build output belongs to the workload that was built | `live_docker`: the workload's `build` stream carries the image build's steps |
| The endpoint returns the VMM's lines | The handler's only source is `RemoteWorkloads::logs` |
| The node keeps no VM log store | `IStorage` has no VM log method; `cargo check -p aseman-node --all-targets` |
| The call graph names the VMM operations again | `docs/migration/current-call-graph.md`: `runEntity` → `launch`, `stopEntity`/`deleteEntity` → `set_state`, `listEntityVms` → `vm_host_call` |

## Rollback

The endpoint's request and response shapes are unchanged, so a legacy client needs no
change. Rolling back means rolling back the node, as P5-06 already requires.
