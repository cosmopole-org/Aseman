# P5-06 delete the embedded VMM and its runtime dependencies from the node

## Deleted

| Node code | Why it can go |
|---|---|
| `drivers/vmm/bridge/` (packet router, runtime IO, gateway control API) | Runtime dispatch is the backend's (A504) |
| `drivers/vmm/host_bridge.rs` (the SDK `VmHost`) | A plugin reaches Aseman only through the guest API |
| `drivers/vmm/bootstrap.rs` | Restoring instances is reconciliation's |
| `drivers/vmm/hostcall_global.rs` (the Go-era callback) | It carried no caller identity (LD-14); the last keyed packets it served are host calls now |
| `drivers/vmm/hostcall_logs.rs` | A workload's logs are its VMM's |
| `drivers/vmm/network/gateway*.rs`, `vm_network.rs` | The VM gateway service was reachable only by a packet type no runtime sends |
| `drivers/vmm/network/docker_host/` | Moved into the native backend, with its tests |
| `Vmm` driver: VM contexts, per-VM write buffers, `vm_db_op`, container registry, runtime registry queries, plan hooks | Runtime and instance state is the backend's; guest data is the creature's database |
| `ICore::begin_vm_trx`/`end_vm_trx` | Their only caller was the deleted bridge |
| `IVmm` | Replaced by `IWorkloads`: signals, alarms, ingress, routes, locks, guest CRUD |
| `NetworkConfig.docker_gateway_port` | The gateway is the backend's; the runtime setting stays with the runtimes |
| node dependencies `caspar-vm-sdk`, `caspar-vm-plugins` | No runtime engine links into the node binary |

## Kept, and why

- The guest host-call surface (`host/`, `hostcall_entities.rs`, `guest_state.rs`) is
  the node's side of the guest API, now reached with an authenticated workload.
- `proxy.rs` (proxy entities), `http_route.rs` and `network/ingress.rs` (ingress and
  custom routes) are node routing, not runtime work.
- `modules/vmm-backend/native-legacy/crates/caspar-vm-plugins` is the backend's
  aggregation crate. RL-014 now tracks replacement of compile-time aggregation with
  signed runtime loading, not a pending directory move.

## Verification

| Gate requirement | Evidence |
|---|---|
| No runtime-engine dependency or competing in-process VMM path in the node | `cargo tree -p aseman-node` names no `caspar-vm-*`, wasmedge, bollard, rquickjs, elpify, or elpian; `dispatch_packet` and the router are gone |
| Obsolete runtime globals, code, and configuration deleted | the table above; `cargo xtask full` |
| The native provider passes parity and VMM conformance | `docs/generated/vmm-native-parity.md` (22 verified), A504 kit, `live_native`, `live_docker`, `system` |
| Every handoff-inventory instance is adopted or explicitly stopped | `aseman-node vmm-handoff` with its digest-bound decisions (P5-05) |
| The node still passes its own suite | `cargo test -p aseman-node --lib` (384 tests; the 11 docker-gateway tests moved to the backend) |

## Rollback

This deletion is not reversible in place: a node of this version needs a VMM. The
runbook's order (Phase 3 cutover, VMM rollout, handoff, then this node) is the
rollback boundary — the previous node binary keeps working until its handoff is
applied.
